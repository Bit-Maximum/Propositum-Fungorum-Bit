ЗАДАЧИ НОРМАЛИЗАЦИИ:

1) НОРМАЛИЗАЦИЯ options
Возможные входные формы options:
A) options уже список объектов (как нужно) → проверь и исправь мелкие несоответствия (см. ниже).
B) options задан как объект с массивами:
   "options": { "label": [ ... ], "value": [ ... ] }
   или иногда только label/value отдельно.
→ Преобразуй в список объектов options, где:
- Количество options = длине списка label (или value, если label отсутствует).
- Для i-го элемента:
  * id = "opt{ i+1 }"
  * label = точная строка из входного label[i] (дословно, без изменений)
  * value = нормализованный токен (см. правило 2) из:
      - value[i], если он есть
      - иначе из label[i]
- Порядок options сохраняй.

2) ПРАВИЛА НОРМАЛИЗАЦИИ value (только если нужно)
Цель: получить стабильный технический токен (snake_case латиницей), без «отсебятины», только как детерминированная функция от исходной строки.
- Если исходный value уже выглядит как токен (латиница/цифры/подчёркивания, начинается с буквы, длина 1–64) — оставь как есть.
- Иначе построй токен так:
  a) Возьми строку-источник (value или label).
  b) Приведи к нижнему регистру.
  c) Транслитерируй кириллицу в латиницу (детерминированно).
  d) Замени любые символы кроме [a-z0-9] на "_" .
  e) Сожми повторяющиеся "_" до одного, обрежь "_" по краям.
  f) Если токен пустой или не начинается с буквы — используй "opt_{i+1}".
  g) Уникальность: если в пределах ОДНОГО узла получились одинаковые value, добавь суффикс "_2", "_3" и т.д. (детерминированно по порядку появления).

3) НОРМАЛИЗАЦИЯ transitions
Возможные проблемы:
- transitions отсутствуют или имеют неправильную структуру.
- condition ссылается на старые значения (которые изменились после нормализации value).
- description отсутствует.

Правила:
A) transitions должны быть списком объектов. Каждый объект должен содержать:
   - condition (строка)
   - target_node_id (строка)
   - description (строка)
B) Если у transition нет description:
   - найди, какому option соответствует condition вида "value == '...'" (или "value == \"...\"")
   - поставь description = option.label (дословно)
   - если определить нельзя — description = "" (не придумывай текст)
C) Обновление condition после изменения value:
   - Внутри каждого узла построй отображение old_value → new_value для options.
     * old_value — исходное value[i] (если было) И/ИЛИ исходная строка из condition в кавычках.
     * new_value — итоговый option.value.
   - В каждом condition замени все совпадения старых значений, которые стоят в кавычках после value == / value !=, на новые new_value.
   - Поддержи частые формы:
     * "value == 'X'"
     * "value == \"X\""
     * "(value == 'X' || value == 'Y')"
     * "value == 'X' && age < 60"  (другие части условия не трогай)
   - НЕ меняй логику условия, только подстановку токенов.
D) Если transitions отсутствуют полностью:
   - НИЧЕГО НЕ ВЫДУМЫВАЙ. Оставь transitions как пустой список [].

4) Q0 НЕ ТРОГАТЬ
- Узел с id="Q0" должен остаться полностью неизменным (включая порядок полей, тексты, transitions и т.п.).
